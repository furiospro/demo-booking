### Задача

В компании два офиса: Москва (Europe/Moscow) и Новосибирск (Asia/Novosibirsk), в каждом есть переговорные. Предыдущий разработчик написал API бронирования, и пользователи жалуются на ошибки. Код — в `app/Http/Controllers/BookingController.php`.

### Часть 1. Ревью

Составьте `REVIEW.md`: перечислите проблемы, для каждой — серьёзность (critical / major / minor) и как исправить. Если место выглядит подозрительно, но проблемой не является, — тоже напишите об этом.

### Часть 2. Доработка

Исправьте `store` и `destroy` так, чтобы выполнялись правила:

- Брони одной комнаты не пересекаются. Встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 — это не пересечение.
- Длительность от 15 минут до 4 часов, шаг 15 минут (10:00, 10:15…).
- Бронь целиком укладывается в рабочее время 09:00–20:00 по местному времени офиса, где находится комната. Клиент присылает время в ISO 8601 с любым смещением.
- Отменить бронь может только её автор.
- Понятные ошибки валидации (422).
- Других ограничений на даты нет.
- Feature-тесты на все правила выше.

Можно менять модели и миграции и добавлять свои классы. Методы `index` и `today` исправлять не нужно, их достаточно разобрать в ревью.

Бонус: при двух одновременных запросах на один слот может создаться двойная бронь. В основной части достаточно, чтобы брони не пересекались при последовательных запросах. Гонку исправьте или опишите в README, как бы вы это сделали.

## DTO

DTO (`app/DTOs`) добавлены для строгой типизации входящих данных. Чтобы не тянуть в проект тяжелый пакет вроде `spatie/laravel-data`, была реализована кастомная логика обработки правил валидации через PHP-атрибуты (`app/DTOs/Attributes`: `Required`, `StringType`, `DateISO`, `Exists` и т.д.).

Можно было остаться в рамках штатных инструментов Laravel из коробки (`$request->validate()` / Form Request), но такой подход дает более чистую архитектуру и легкую навигацию по проекту: правила объявлены рядом с полями DTO, а не размазаны по контроллерам и реквестам.

Затраты на рефлексию при разборе атрибутов в данном случае минимальны и не оказывают влияния на производительность при штатных нагрузках.

## Логирование

Логи бронирований пишутся в отдельный канал `bookings` (`storage/logs/bookings.log`, см. `config/logging.php`). Разделение каналов может быть необходимо (например, доменные логи отдельно от общесистемных), но повсеместно вызывать логгер через фасад `Log::channel('bookings')` и каждый раз прописывать канал неудобно. Выбор канала относится к настройке приложения, а не к бизнес-логике, поэтому нужный логгер внедряется через DI: интерфейс `App\Logging\BookingLoggerInterface` связывается с реализацией `BookingLogger` в `AppServiceProvider`, а контроллер и сервис просто принимают интерфейс в конструктор.

Для трассировки запросов middleware `AssignRequestId` берет `request_id` из входящего заголовка `X-Request-Id` (сквозная трассировка между сервисами) либо генерирует новый UUID и добавляет его в общий контекст через `Log::shareContext()`. В результате `request_id` попадает в записи всех каналов — это демонстрация общего контекста лога между каналами.

Для решения гонки при создании записи воспользовался средствами самой СУБД. Был добавлен индекс gist и ограничение на поля starts_at, ends_at, room_id. Исключения от postgres при возникновении огрананичения на вставку отдельно обрабатываются для выдачи соответствующей ошибки. Таким образом экономим запросы в бд для проверки записи. Для обеспечения оптимистичной блокировки в коде можно исползовать редис и отсекать дублирующие запросы до похода в бд. Также в redis можно хранить зарегистрированные записи с временем жизни - конец суток записи. Таким образом можно отсекать дубли и проверять наложения. Так как в docker файле не был описан сервис redis, решил остаться в рамках доступных сервисов

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "user_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Лог созданных броней пишется в `storage/logs/bookings.log`.
